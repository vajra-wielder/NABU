# NABU v0.1: review and replication

NABU v0.1 (Python, early 2025) was added to this repository as
`NABU_V0.1/` in commit `8a64176` ("Old Nabu version"). It was reviewed in
full, every process it set out to do was replicated in the current NABU,
and the folder was then removed. It remains in the git history:
`git show 8a64176 --stat`, or `git checkout 8a64176 -- NABU_V0.1` to bring
it back.

## What v0.1 was

A Windows-only desktop app on a pen drive:

| File | Role |
|---|---|
| `run.bat` | Launcher: finds the bundled `python\python.exe`, builds `data\wikipedia.db` if missing (`run.bat --rebuild` forces it), then opens the GUI |
| `python\` | Portable Python 3.13 (Windows x64 embeddable, ~10 MB, 28 files) |
| `requirements.txt` | lxml, mwparserfromhell, Pillow, PyQt5, to be installed into `python\Lib\site-packages` |
| `scripts\index_handler.py` | Read the multistream index into a `{title: offset}` dictionary |
| `scripts\parser.py` | Create the SQLite schema and fill it from the dump: 8 tables |
| `scripts\utils.py` | The extraction functions again (copy of those in `parser.py`) |
| `scripts\search.py` | Full-text search with SQLite FTS5 over title and content |
| `scripts\gui.py` | PyQt5 window: search box, results pane, hyperlink navigation |
| `data\wikipedia.db` | The SQLite database: schema only, 0 rows in every table |
| `README.html`, `Testing.txt`, `data\What to put here.txt` | Notes: features, folder layout, the dump files to supply, dump of 13 March 2025 |

The database schema (from `parser.py`), one row per item per article:

| Table | Columns | Extraction |
|---|---|---|
| `articles` | id, title, content | the page's wikitext |
| `links` | source_article_id, target_article_title | `[[...]]` |
| `glossary` | article_id, term, definition | `{{glossary\|term\|definition}}` |
| `geodata` | article_id, latitude, longitude | `{{coord\|lat\|lon}}` |
| `tables` | article_id, table_data | `<table>` tags via mwparserfromhell |
| `media` | article_id, media_type, media_url | `[[File:...]]`, `[[Image:...]]` |
| `infoboxes` | article_id, infobox_data | templates whose name starts with `Infobox` |
| `metadata` | article_id, metadata_type, metadata_value | categories and templates |

Promised features (README): search by title or content; hyperlinks;
glossary; geographical data on a map; tables; images and media;
infoboxes; categories and templates.

## State of v0.1 as found

The design was sound, but the code could not run end to end:

1. **Dependencies were never bundled.** `python\` holds only the
   standard runtime. `Lib\site-packages` is absent, so `import PyQt5` and
   `import mwparserfromhell` fail before anything happens.
2. **The index was parsed as XML.** Wikimedia's index is plain text
   (`offset:pageid:title` per line), and its real name ends in
   `-index.txt.bz2`, not `-index.xml.bz2` as `index_handler.py`,
   `README.html` and `What to put here.txt` say. Every line failed to
   parse and was skipped, so the index was always empty.
3. **Offsets were applied to the wrong stream.** `parse_dump` opened the
   dump with `bz2.open` and seeked with *compressed* offsets inside the
   *decompressed* data. It then read a single line as if it were a
   whole `<page>`. No article could have been found.
4. **`search.py` crashes**: it uses `sys` without importing it. It also
   re-inserted every article into the FTS table on *every* search, so
   the table doubled each time.
5. **The GUI's database handle was `None`** whenever the database
   already existed (`setup_database` returns `None` then). Hyperlink
   following (`follow_hyperlink`) was defined but never connected to
   anything, and results were shown as raw wikitext.
6. **Extraction details:** `extract_tables` filtered tags named
   `table`, which misses wikitext tables (`{| ... |}`).
   `extract_coordinates` kept only the first two `{{coord}}` parameters,
   which is wrong for degree/minute/second forms. The `{{glossary|t|d}}`
   form it looked for is not how Wikipedia writes glossaries
   (`{{term}}`/`{{defn}}`). The `metadata` regex `\{\{(.*?)\}\}` breaks
   on nested templates.
7. **Scale:** storing every article's wikitext in SQLite would have
   made a database bigger than the dump itself. English Wikipedia
   uncompressed is about 100 GB, more than the pen drives it targets.

The empty `wikipedia.db` confirms the parser never completed a run.

## What did not carry over, deliberately

- **SQLite.** Go's standard library has no SQLite, and copying the
  dump into a database would multiply its size. NABU reads the
  compressed dump in place and keeps compact indexes beside it. `nabu
  export` produces the same per-article data as JSON lines, which load
  into SQLite in one step if wanted (`sqlite-utils insert db pages
  file.jsonl --nl`, or Python's `json` + `sqlite3`).
- **The Windows-only portable Python** and its 28 files. One static
  program per platform replaces it.
- **The `links` table as a store.** Outgoing links are extracted on
  demand (page data, export). "What links here" (backlinks) was never a
  v0.1 feature and remains possible future work.
